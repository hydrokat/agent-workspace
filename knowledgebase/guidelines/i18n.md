# Internationalization (i18n) Guidelines

This document outlines the architecture, standards, and workflow for internationalization (i18n) within the task tracker web application.

## Core Principles

1. **No Hardcoded Copy**: All user-facing text strings—including headings, labels, button text, field placeholders, empty states, error messages, `aria-label`s, and layout metadata—must be externalized into the localized dictionary files.
2. **Type-Safe Dictionaries**: To prevent missing keys or structural gaps at build time, all dictionaries must implement the canonical type schema defined by the primary `en` locale.
3. **Cookie-Based Locales**: The application resolves the active language via the `NEXT_LOCALE` cookie. The URL segment `[lang]` is omitted to prevent session-sync and routing collisions with Supabase Auth in the root layout.

---

## Technical Architecture

### 1. Locale Configuration

Locales are declared and type-guaranteed under `lib/i18n/config.ts`:

```typescript
export const locales = ['en', 'en-simple'] as const;
export type Locale = (typeof locales)[number];
export const defaultLocale: Locale = 'en';

export function isLocale(value: string): value is Locale {
  return locales.includes(value as Locale);
}
```

### 2. Dictionaries

- **Directory**: `lib/i18n/dictionaries/`
- **Source of Truth (`en.ts`)**: Defines the canonical schema.
- **Plain Vocabulary (`en-simple.ts`)**: Implements `Dictionary` and mirrors the keys exactly:

```typescript
import { Dictionary } from './en';
export const enSimple: Dictionary = {
  // Must contain identical key-structure
};
```

### 3. Server Resolution (`lib/i18n/server.ts`)

Server-side pages and layouts resolve the locale and fetch the dictionary using standard Next.js headers/cookies APIs:

```typescript
export async function getLocale(): Promise<Locale>;
export async function getDictionary(locale: Locale): Promise<Dictionary>;
```

**Resolution Priority**:
1. `NEXT_LOCALE` cookie value.
2. `Accept-Language` request headers.
3. Fallback to `en`.

## Implementation Patterns

### Server Components

Server Components retrieve the locale and load the dictionary natively inside the server context:

```typescript
import { getLocale, getDictionary } from '@/lib/i18n/server';

export default async function Page() {
  const locale = await getLocale();
  const dict = await getDictionary(locale);

  return (
    <div>
      <h1>{dict.dashboard.welcome}</h1>
    </div>
  );
}
```

### Passing Dictionaries to Client Components

To maintain efficiency and minimize hydration payloads, Server Components must slice out only the relevant namespace from the dictionary before passing it to Client Components:

```typescript
// Server Page / Layout
const locale = await getLocale();
const dict = await getDictionary(locale);

return <ClientComponent currentLocale={locale} dashboardDict={dict.dashboard} />;
```

### Language Switcher

The language switcher component (`components/language-switcher.tsx`) invokes the `setLocale` Server Action, writing the cookie to the client browser, and reloads Server Components using `router.refresh()`:

```typescript
'use client';
import { useTransition } from 'react';
import { useRouter } from 'next/navigation';
import { setLocale } from '@/lib/actions/i18n';

// inside the component:
const router = useRouter();
const [isPending, startTransition] = useTransition();

const handleSwitch = (locale: string) => {
  startTransition(async () => {
    await setLocale(locale);
    router.refresh();
  });
};
```

## Adding a New Locale

To add a new language to the system:
1. Register the new locale in the `locales` array in `lib/i18n/config.ts`.
2. Create the typed dictionary module in `lib/i18n/dictionaries/<locale-code>.ts` that implements the `Dictionary` interface.
3. Import and map the new dictionary loader under `dictionaries` inside `lib/i18n/server.ts`.
4. Run `npm test` to trigger the **Parity Validation Test**, ensuring all keys have been mapped.
