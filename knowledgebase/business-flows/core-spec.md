# HTN Points System — High Level Spec (v3)

---

## 🎯 Purpose

A web app that converts:

**event contribution → points → rewards**

into a fair, transparent, and gamified system.

Designed to:

- reward real contributors
- encourage teamwork
- remain configurable per event

---

# 👥 Users (Supabase-Based)

User authentication is handled by:

- Supabase (`auth.users`)

### App-Level User Concepts

We do **not store users locally**, but we extend them via:

### `team_members`

Represents a user inside the system.

Fields:

- `user_id (UUID)` → references `auth.users.id`
- `team_id`
- `member_type` → `member | apprentice`

---

## 🧑‍💼 Admins

Admins are **not a separate table**.

Handled via:

- Supabase auth metadata **OR**
- hardcoded allowlist (MVP)

Admins can:

- manage teams
- manage members
- create tasks
- approve participation
- approve submissions
- approve rewards
- configure points and rewards

---

# 🏢 Teams

Formerly “committees”

### Structure

- `teams`
  - `id`
  - `name`
  - `team_lead_id (UUID)`

### Rules

- A user can belong to **multiple teams** (via `team_members`)
- A team may have **one lead (optional)**

# 📌 Core Modules

---

## 1️⃣ Team Management

Admin can:

- create teams
- view detailed team personnel registry (`/admin/teams/[id]`)
- search for existing profiles to assign to teams
- invite new users by email with autogenerated passwords
- manage member roles and remove personnel
- assign a team lead


---

## 2️⃣ Task Management

Tasks represent real event work.

### Task Fields

- `title`
- `description`
- `team_id`
- `category_id` — **required**; every task belongs to exactly one category
- `base_points` (admin-defined)
- `deadline` (optional)
- role limits:
  - `max_leads`
  - `max_contributors`
  - `max_assistants`

### Notes

- Tasks belong to a team
- Tasks can have multiple participants
- Tasks must have a category; use the seeded "General" category when no specific category applies

## 2b. Task Categories

Admin-managed categories that group tasks and optionally cap point accumulation per user.

### `task_categories` Fields

- `id BIGSERIAL`
- `name VARCHAR(100) UNIQUE`
- `description TEXT` (optional)
- `point_cap INT DEFAULT 0` — 0 = unlimited; positive = max awarded points per user per reset window
- `cap_reset_period VARCHAR` — `'day' | 'week' | 'month'`

### Per-Category Point Capping

When `point_cap > 0`, a user who has accumulated `>= point_cap` awarded points in the current window cannot claim further tasks in that category until the window resets or an admin manually resets the cap. See [Category Point Capping](../best-practices/category-point-capping.md) for the full design.

---

## 3️⃣ Team Task System

Each task supports multiple contributors with roles.

### Roles (app-level enum)

- `lead`
- `contributor`
- `assistant`

Stored as string (`VARCHAR`)

---

### Participation Flow

1. Member applies to task with a role
2. Admin approves participation
3. Member works on task

---

### Table: `task_participations`

Fields:

- `task_id`
- `user_id (UUID)`
- `role`
- `status` → `pending | approved | rejected`
- `approved_at`

Constraints:

- one user per task (`unique(task_id, user_id)`)

---

## 4️⃣ Task Completion Workflow

1. Member submits proof
2. **Admin or team lead** reviews the submission
3. Reviewer approves/rejects (team leads cannot approve their own submissions)
4. Points awarded **only after approval**

See [Submission Vouching Pattern](../best-practices/submission-vouching-pattern.md) for the full authorization model.

---

### Table: `task_submissions`

Fields:

- `task_participation_id`
- `proof`
- `status`
- `admin_feedback` (populated on rejection)
- `reviewed_by UUID` — who approved/rejected
- `reviewed_at TIMESTAMPTZ`

---

# ⭐ Points Engine (Configurable)

---

## Base Concept

Points are derived from:

task.base_points × role multiplier

---

## Role Multipliers (Configurable)

### Table: `role_point_configs`

| role        | multiplier |
| ----------- | ---------- |
| lead        | 1.0        |
| contributor | 0.6        |
| assistant   | 0.3        |

Admin can modify anytime.

---

## Point Storage (Important)

### Table: `point_transactions`

Fields:

- `user_id (UUID)`
- `task_participation_id`
- `base_points`
- `multiplier`
- `computed_points`
- `source` → `task | bonus | adjustment`

### Notes

- This is the **source of truth**
- Do NOT rely only on computed totals

---

## Point Awarding Flow

Triggered when:

- submission is **approved**

Steps:

1. get `task.base_points`
2. get `role multiplier`
3. compute points
4. insert into `point_transactions`

---

# 🎁 Rewards System (Fully Configurable)

---

## Rewards Definition

### Table: `rewards`

Fields:

- `name`
- `description`
- `points_required`
- `reward_type` (ticket, discount, etc.)
- `reward_value` (e.g. % discount)
- `is_active`

---

## Reward Claiming

### Table: `reward_claims`

Fields:

- `user_id (UUID)`
- `reward_id`
- `status` → `pending | approved | rejected`
- `approved_at`

---

## Reward Flow

1. User reaches required points
2. User submits claim
3. Admin approves
4. Reward granted

# 🏆 Leaderboards

A non-realtime leaderboard system allows users to view point rankings.

### Team Leaderboard
Shows the highest total points accumulated by a team.

### Individual Leaderboard
Shows the highest points gained by an individual user.

### Leaderboard Rules
- Top 1-10 are highlighted in descending order.
- Paginated with a customizable "per page" setting.
- The user's current rank is always shown as the 11th item (unless they appear in the current page).
- Refreshed on load (non-realtime).

# 🔁 Core Flow (End-to-End)

1. Admin creates teams
2. Admin assigns members
3. Admin creates tasks
4. Members claim tasks
5. Admin approves participation
6. Members submit proof
7. Admin approves submission
8. System awards points
9. Members reach reward threshold
10. Members claim rewards
11. Admin approves rewards

---

# ⚠️ System Constraints (Handled in App Layer)

Since we removed DB enums:

### Must enforce in app:

- valid roles
- valid statuses
- valid sources

---

### Must enforce via logic:

- max participants per role
- one submission per participation
- reward eligibility (points >= required)

---

# 🔐 Supabase Considerations

### Row Level Security (RLS)

Policies needed for:

- users accessing only their records
- admins accessing everything

---

### Auth Mapping

Use:

auth.uid()

to map logged-in user to:

- `team_members.user_id`
- `task_participations.user_id`
- etc.
