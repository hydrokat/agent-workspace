# HTN Points System — High Level Spec (v3)

---

## 🎯 Purpose

A web app that converts:

**event contribution → points → rewards**

into a fair, transparent, and gamified system.

Designed to:

- reward real contributors
- encourage teamwork
- remain configurable per event

---

# 👥 Users (Supabase-Based)

User authentication is handled by:

- Supabase (`auth.users`)

### App-Level User Concepts

We do **not store users locally**, but we extend them via:

### `team_members`

Represents a user inside the system.

Fields:

- `user_id (UUID)` → references `auth.users.id`
- `team_id`
- `member_type` → `member | apprentice`

---

## 🧑‍💼 Admins

Admins are **not a separate table**.

Handled via:

- Supabase auth metadata **OR**
- hardcoded allowlist (MVP)

Admins can:

- manage teams
- manage members
- create tasks
- approve participation
- approve submissions
- approve rewards
- configure points and rewards

---

# 🏢 Teams

Formerly “committees”

### Structure

- `teams`
  - `id`
  - `name`
  - `team_lead_id (UUID)`

### Rules

- A user can belong to **multiple teams** (via `team_members`)
- A team may have **one lead (optional)**

---

# 📌 Core Modules

---

## 1️⃣ Team Management

Admin can:

- create teams
- view detailed team personnel registry (`/admin/teams/[id]`)
- search for existing profiles to assign to teams
- invite new users by email with autogenerated passwords
- manage member roles and remove personnel
- assign a team lead


---

## 2️⃣ Task Management

Tasks represent real event work.

### Task Fields

- `title`
- `description`
- `team_id`
- `base_points` (admin-defined)
- `deadline` (optional)
- role limits:
  - `max_leads`
  - `max_contributors`
  - `max_assistants`

### Notes

- Tasks belong to a team
- Tasks can have multiple participants

---

## 3️⃣ Team Task System

Each task supports multiple contributors with roles.

### Roles (app-level enum)

- `lead`
- `contributor`
- `assistant`

Stored as string (`VARCHAR`)

---

### Participation Flow

1. Member applies to task with a role
2. Admin approves participation
3. Member works on task

---

### Table: `task_participations`

Fields:

- `task_id`
- `user_id (UUID)`
- `role`
- `status` → `pending | approved | rejected`
- `approved_at`

Constraints:

- one user per task (`unique(task_id, user_id)`)

---

## 4️⃣ Task Completion Workflow

1. Member submits proof
2. Admin reviews
3. Admin approves/rejects
4. Points awarded **only after approval**

---

### Table: `task_submissions`

Fields:

- `task_participation_id`
- `proof`
- `status`
- `approved_at`

---

# ⭐ Points Engine (Configurable)

---

## Base Concept

Points are derived from:

task.base_points × role multiplier

---

## Role Multipliers (Configurable)

### Table: `role_point_configs`

| role        | multiplier |
| ----------- | ---------- |
| lead        | 1.0        |
| contributor | 0.6        |
| assistant   | 0.3        |

Admin can modify anytime.

---

## Point Storage (Important)

### Table: `point_transactions`

Fields:

- `user_id (UUID)`
- `task_participation_id`
- `base_points`
- `multiplier`
- `computed_points`
- `source` → `task | bonus | adjustment`

### Notes

- This is the **source of truth**
- Do NOT rely only on computed totals

---

## Point Awarding Flow

Triggered when:

- submission is **approved**

Steps:

1. get `task.base_points`
2. get `role multiplier`
3. compute points
4. insert into `point_transactions`

---

# 🎁 Rewards System (Fully Configurable)

---

## Rewards Definition

### Table: `rewards`

Fields:

- `name`
- `description`
- `points_required`
- `reward_type` (ticket, discount, etc.)
- `reward_value` (e.g. % discount)
- `is_active`

---

## Reward Claiming

### Table: `reward_claims`

Fields:

- `user_id (UUID)`
- `reward_id`
- `status` → `pending | approved | rejected`
- `approved_at`

---

## Reward Flow

1. User reaches required points
2. User submits claim
3. Admin approves
4. Reward granted

---

# 📊 Member Dashboard

Users can see:

- total points (sum of transactions)
- tasks joined
- tasks completed
- reward eligibility
- claimed rewards

---

# 🛠 Admin Dashboard

Admins manage:

- teams
- members
- tasks
- participation approvals
- submission approvals
- rewards
- role point configs

---

# 🔁 Core Flow (End-to-End)

1. Admin creates teams
2. Admin assigns members
3. Admin creates tasks
4. Members claim tasks
5. Admin approves participation
6. Members submit proof
7. Admin approves submission
8. System awards points
9. Members reach reward threshold
10. Members claim rewards
11. Admin approves rewards

---

# ⚠️ System Constraints (Handled in App Layer)

Since we removed DB enums:

### Must enforce in app:

- valid roles
- valid statuses
- valid sources

---

### Must enforce via logic:

- max participants per role
- one submission per participation
- reward eligibility (points >= required)

---

# 🔐 Supabase Considerations

### Row Level Security (RLS)

Policies needed for:

- users accessing only their records
- admins accessing everything

---

### Auth Mapping

Use:

auth.uid()

to map logged-in user to:

- `team_members.user_id`
- `task_participations.user_id`
- etc.
